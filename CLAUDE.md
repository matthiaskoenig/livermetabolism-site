# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Static site source for the König research group site (https://www.livermetabolism.com/), built with [Astro](https://astro.build/) (static output), [Vue](https://vuejs.org/) components (statically rendered, with a handful of small hydrated islands), and plain TypeScript for the site chrome, styled with Tailwind v4. A small Python/uv package under `src/` generates Typst-formatted content (publication lists, CV, funding, presentations, etc.) from the same YAML data used by the Astro site. That YAML data has a pydantic schema (`src/data.py`) mirrored by a Zod schema (`site/lib/schemas.ts`) — see "Data model & validation" below before editing `data/*.yml` by hand.

## Repository layout

- `site/` — Astro site source (Astro's own default `src/` is taken by the Python package here, so the app lives under `site/` instead). `pages/` are routes (`.astro`); `layouts/` wraps them; `components/` holds both `.astro` templates (the site chrome, each with its own bundled `<script>`) and Vue SFCs (entry cards, rows, and modals — rendered statically); `lib/` is the shared TypeScript (data loading, URL/asset helpers, modals, search, icons — each with a co-located `*.test.ts`); `styles/global.css` is the Tailwind theme plus ported rules; `content.config.ts` defines Astro's content-layer collections over `data/*.yml`.
- `data/` — the single database: YAML tables (publications, people, projects, software, presentations, posters, funding, news, activities, editors, panels, teaching, abstracts, meetings, linkedin, plus `tags.yml`/`country_flags.yml` reference tables), validated by both `src/data.py` (pydantic, Python tooling) and `site/lib/schemas.ts` (Zod, the Astro build) — keep the two schemas in sync when adding a field.
- `public/` — static files served as-is at `/...` (`assets/image/`, `assets/pdf/`, `assets/cv/`, favicon). `assets/image/graph/` (`people/`, `projects/`, `software/`, `topics/`) holds the network-graph node thumbnails generated by `npm run graph:thumbs` — committed output, like the 128 px avatars, never built on the fly.
- `assets_src/` — raster masters of the images; not served, only their `.webp` renditions under `public/assets/image/` are.
- `src/` — standalone Python package (not part of the Astro build). `src/data.py` is the pydantic data model for `data/*.yml` (see below). Each `src/cv/list_of_*.py` script reads one `data/*.yml` file into a pandas DataFrame and renders it to a Typst (`.typ`) file in `src/cv/results/`, e.g. for the CV. Scripts are invoked as modules (`uv run python -m src.cv.list_of_publications`), not via a CLI entrypoint — edit the `selected`/`highlights` sets at the bottom of a script to change what gets included in a given output. Not every `data/*.yml` file has a corresponding generator script.
- `tests/` — pytest suite for `src/data.py` (model validators, cross-reference checks, end-to-end YAML loading). Run via `uv run pytest tests/`; also runs in CI (the `validate` job of `.github/workflows/site.yml`) on every push/PR.
- `e2e/` — Playwright specs (`interactions.spec.ts`, `pages.spec.ts`) using base-relative paths (see `playwright.config.ts`, which derives `baseURL` from the `BASE` env var).
- `nginx/`, `docker-compose*.yml`, `deploy.sh` — self-hosted deployment (see Branches and deployment).
- `scripts/` — standalone Node/TypeScript tooling, run directly by Node 24 (no build step, so imports inside `scripts/` and into `site/lib/` carry the `.ts` extension). `fetch-github.ts` writes the GitHub snapshot (see "Live GitHub and Scholar data"), with `lib/repos.ts`, `lib/github-client.ts` and `lib/transform.ts` beside it, `fetch-scholar.ts` writes the Scholar snapshot with `lib/scholar.ts` beside it, and `fetch-citations.ts` writes the OpenAlex citation snapshot with `lib/openalex.ts` beside it, each with a co-located `*.test.ts` run by the same vitest config as `site/`; the recorded GitHub API responses, Scholar profile page and OpenAlex response used by those tests live in `tests/fixtures/github/`, `tests/fixtures/scholar/` and `tests/fixtures/openalex/`.
- `scripts/graph-thumbs.ts` — one-off/maintenance generator of the network-graph thumbnails (`npm run graph:thumbs`), the only place `sharp` (a dependency of Astro) is used; the source-to-target mapping is the pure, unit-tested `scripts/lib/graph-thumbs.ts`.
- `scripts/fetch-icons.sh` — downloads the Font Awesome Free 6 SVGs into `site/icons/*.svg` (40 SVGs), named by the Font Awesome 4 class names the site uses; `data/tags.yml` keeps the FA4 `icon` names that select among them. `scripts/reindent_yaml.py` — one-off/maintenance fixer for the YAML indentation rule below.
- `science_communication/` — planning notes and strategy documents (not part of the build).

## Data model & validation

`src/data.py` defines a pydantic model for every table in `data/*.yml`, and cross-validates the relationships between them: `people: list[str]` fields (on publications/projects/software/news/teaching/presentations/posters/panels/abstracts) must resolve to real `people.yml` ids, `tags: list[str]` must be tags defined in `tags.yml`, `publications: list[str]` (on projects/software/presentations/panels) must resolve to real `publications.yml` ids, ids must be unique within their table, and referenced image/pdf files must exist under `public/assets/image/`/`public/assets/pdf/` — including `publications.pdf` and `funding.funder_logo` (see `IMAGE_FIELDS` in `src/data.py`).

After **any** manual edit to `data/*.yml`, run:
```bash
uv run python -m src.data
```
This loads and validates all of it, printing every problem found (not just the first) and exiting non-zero on failure — the same check `tests/test_real_data.py` runs in CI, so a bad edit fails the build before merge rather than silently breaking the live site.

`js-yaml` (the parser the Astro build uses) follows YAML 1.2, which requires the continuation lines of a multi-line quoted string to be indented **deeper than their key** — PyYAML accepts them flush with the key, `js-yaml` rejects the file with "deficient indentation". Keep new multi-line values indented, or run `uv run python scripts/reindent_yaml.py` (`--check` reports without writing), which re-indents only those continuation lines and refuses to write if `yaml.safe_load()` no longer returns the same object.

The Astro build re-validates the same YAML independently through `site/lib/schemas.ts` (Zod schemas wired into `content.config.ts`'s collection loaders) and fails the build on a dangling `people`/`tags`/`publications` reference — the two schemas must be kept in sync by hand when a field is added or changed.

Astro's content layer does **not** preserve a YAML file's row order (it persists collections sorted alphabetically by id for deterministic build caching). The `yml()` loader in `content.config.ts` injects an `order` field recording each row's original position; `all()` in `site/lib/data.ts` sorts by it and strips it back out before returning, and `getTags()` goes through `toTagInfo()` in `site/lib/views.ts` to do the same for tags. Any new collection that cares about display order must go through `yml()`/`all()` rather than calling `getCollection()` directly.

`site/lib/data.ts`'s `all<K extends keyof CollectionData>(key: K)` infers its return type from `key` alone via a `CollectionData` interface mapping every collection it serves to its schema type — add a new collection there (not as a caller-supplied generic) when adding a `get*()` wrapper.

Field names are unified across tables for the same concept: `people` is always the internal-person-id list (as opposed to `authors`, the free-text bibliographic string with affiliations/superscripts); `tags` always references `tags.yml`; `homepage` is always "this thing's own/associated external URL" (not `project`); `event`/`event_page` is always the conference/meeting a talk/poster/abstract belongs to (not `meeting`/`webpage`); `tenure` is always a free-text period range like `"2020-2025"` (not `year`/`term`, which were ambiguous with the single-year `int` used on bibliographic entries); `role` is a person's list of positions held (not `position`, which on `Publication` means author-order instead). Country flags are looked up from `country_flags.yml` by `person.country` rather than stored per-person.

## Live GitHub and Scholar data

The software/research page shows live GitHub data (stars, latest release, issues, last push, release feed, commit activity) that must stay current **without a redeploy**, so it does not go through the Astro build's data pipeline:

- `scripts/fetch-github.ts` reads the `repository` URL of every `data/software.yml` entry (normalised to `owner/name` and deduplicated by `scripts/lib/repos.ts` — two entries may share a repository), calls the GitHub REST API per repository (metadata, up to 20 releases, the latest commit, 52 weeks of commit activity — from `/stats/commit_activity`, falling back to `/stats/participation` for a repository whose statistics GitHub is still computing; `scripts/lib/github-client.ts`, four repositories in flight), transforms the responses into the snapshot shape (`scripts/lib/transform.ts`, pure and unit-tested against the fixtures) and writes `github.json` atomically to the path given as its argument (default `./github.json`, gitignored).
- `.github/workflows/github-data.yml` (`github-data` job, daily at 05:00 UTC plus `workflow_dispatch`) runs the fetch with the Action's default `GITHUB_TOKEN` and commits `github.json` to the **orphan branch `github-data`**, which holds nothing but that file and `scholar.json` (below). `site.yml` runs only on `main` and pull requests, so that push never triggers a build or deploy — keep it that way.
- The site reads the snapshot from `SNAPSHOT_URL` (`https://raw.githubusercontent.com/.../github-data/github.json`) twice: `site/lib/github.ts`'s `loadSnapshot()` in `astro build` (10 s timeout, `emptySnapshot()` + a warning on any failure, so GitHub being down cannot fail the build) server-renders everything, and `site/lib/githubLive.ts`'s `loadLiveSnapshot()` (one memoized fetch per page load, `null` on failure) refreshes it in the browser — that is what keeps the page current between deploys. `raw.githubusercontent.com` is therefore in the CSP's `connect-src`.
- The snapshot is keyed by the `owner/name` derived from `data/software.yml`, which is **not** always what GitHub calls the repository today (`matthiaskoenig/libsbgn-python` is `matthiaskoenig/libsbgnpy` there now): every row's `repo`/`fullName` and the card's `data-repo` attribute carry that key, so the browser-side refresh finds the same entry again, while links use the entry's own `htmlUrl`.
- `site/lib/githubRows.ts` holds every projection of the snapshot (`statsFor`, `latestReleases`, `releaseTimelineRows`, `starsRows`, `activityRows`, `relativeDate`, `shortDate`, `hasData`) as pure functions, so the build and the browser compute the same rows; `site/lib/chartOptions.ts` turns those rows into ECharts options. The commit chart stacks at most ten series (`ACTIVITY_SERIES`): with more active repositories the nine most active keep their palette colour and the rest are stacked as one grey "N others" series, listed per repository in its tooltip, so a colour never stands for two repositories as `data/software.yml` grows. On `research.astro` the rows are props of four `client:visible` islands (`ReleaseFeed.vue`, `ReleaseTimeline.vue`, `CommitActivityChart.vue`, `StarsChart.vue`, the last three through `useChart.ts`), each of which re-computes its rows when `loadLiveSnapshot()` returns something newer than the build's `fetchedAt`; the per-card `.software-stats` lines (`SoftwareCard.vue`, `[data-repo]` with `[data-field]` spans, rendered — with every field `hidden` — for any GitHub repository even when the build had no data for it) are patched in place by `site/lib/githubStats.ts` from the bundled script of `SoftwareLive.astro`, which also renders the "Data from GitHub, updated …" note.
- ECharts is imported from `echarts/core` with only the used pieces (bar + line + scatter + graph series, grid/tooltip/legend/dataZoom, `CanvasRenderer`) — still a ~200 KB gzipped chunk (the `GraphChart` of the network page is 14 KB of it), which is why it loads only on the research, publications and network pages, and everywhere but `/network/` only once a chart scrolls into view. Tooltips use `renderMode: 'richText'` (drawn in the canvas): an HTML tooltip would inject inline styles and trip the CSP. Chart heights are set through the CSSOM in `useChart.ts` for the same reason.
- `site/lib/githubSchema.ts` is the single source of truth for the snapshot shape (`fetchedAt`, `repos[fullName]`, `releases[fullName]`), shared by the script that writes it and every read; all schemas are `.strict()`, and the fetch parses its own output before writing, so writer and reader can never drift apart silently. `emptySnapshot()` (`fetchedAt` = epoch, so any real snapshot is newer) is the fallback when a read fails.
- The snapshot carries **text only**: release bodies are reduced to a plain-text `summary` (first paragraph, markdown stripped, ≤300 characters, `summarize()`). Never insert snapshot content as HTML.

Run the fetch locally (the token only needs public read access):

```bash
GITHUB_TOKEN=$(gh auth token) npm run fetch:github -- github.json
```

The same workflow, the same branch and the same schema-in-the-middle pattern carry a second snapshot, `scholar.json`, for the Google Scholar citation metrics:

- `scripts/fetch-scholar.ts` fetches the public profile page (`SCHOLAR_USER_ID`, browser-like `User-Agent`) and parses it with `scripts/lib/scholar.ts` — regex-based on the page's stable ids/classes (`gsc_prf_in`, `gsc_rsb_st`, `gsc_g_t`/`gsc_g_a`), no HTML library, every missing part throwing a precise message so a layout change is visible in the workflow log. Scholar has no API; the only alternatives were a paid third party or a different, lower citation count.
- The path argument (`../data/scholar.json` in the workflow) is **both** the previous snapshot and the output: `buildScholarSnapshot()` carries the previous `history` forward and `mergeHistory()` keeps one point per UTC day, so the citations-over-time series accumulates run by run. Never delete `scholar.json` from the `github-data` branch — the history only exists there.
- A blocked request (non-200, a redirect to `/sorry/`, the CAPTCHA form) throws with a message starting with `blocked` and **writes nothing**; `fetch-scholar.ts`'s `fetchProfileHtmlWithRetry` retries such a failure up to 3 attempts (30 s, then 60 s apart) before giving up, since the GitHub-hosted runner gets an occasional transient 403, while a `no stats table` (page layout changed) or any other error is never retried; the workflow step is `continue-on-error: true` and runs after the worktree is prepared, so a blocked run neither fails the GitHub snapshot nor replaces the last good `scholar.json`.
- `site/lib/scholarSchema.ts` is the single source of truth for the shape (`fetchedAt`, `profile`, `sinceYear`, `citations`/`hIndex`/`i10Index` as `{all, since}`, `citationsPerYear`, `history`), `.strict()` throughout, with `emptyScholar()` (epoch `fetchedAt`) as the fallback and `SCHOLAR_URL` the raw URL on the `github-data` branch. `tests/fixtures/scholar/profile.html` is a recorded, trimmed copy of the real profile page that the parser tests run against.
- Visitors' browsers never contact Google: only the snapshot on `raw.githubusercontent.com` is fetched. The only free-text field is the profile name — rendered as text, never as HTML.
- On `publications.astro` the snapshot is read once at build time (`site/lib/scholar.ts`'s `loadScholar()`, same 10 s timeout / `emptyScholar()` fallback as the GitHub read) and projected by the pure helpers of `site/lib/scholarRows.ts` (`perYearRows`, `historyRows`, `stripValues`, `historyNote`, `profileHref`; the date helpers come from `githubRows.ts`). `ScholarStats.astro` renders the `<section id="scholar">` summary strip — citations / h-index / i10-index as `[data-field]` spans with their "since <year>" lines, plus the site's own peer-reviewed publication count from `data/publications.yml` (status `publication`, `review`, `proceeding` or `chapter`), which is **not** a Scholar number — and its bundled script patches them in place through `site/lib/scholarStats.ts` when `loadLiveScholar()` (`site/lib/scholarLive.ts`, memoized per page load) returns something newer. A build without a snapshot renders the metric figures empty and `hidden`; the runtime fills them in and unhides them, so the page never shows zeros as metrics.
- The two `client:visible` charts are `CitationsPerYearChart.vue` (Scholar's histogram as bars) and `CitationHistoryChart.vue` (year-end totals derived from the histogram — the undated remainder of Scholar's total as a baseline — followed by the accumulated daily readings, as a line on a time axis, `symbol` shown and a "history starts <date>" caption so the very first one-point series still reads as a chart), both through `useChart.ts` (which registers `LineChart` for them) and `citationsPerYearOption`/`citationHistoryOption` in `site/lib/chartOptions.ts`. The profile URL is never patched at runtime: `profileHref()` rejects anything that is not a `https://scholar.google.com/` URL and falls back to the URL derived from `SCHOLAR_USER_ID`, so a string from the snapshot can never become an `href` the page did not build itself.

```bash
npm run fetch:scholar -- scholar.json
```

A third snapshot, `citations.json`, carries the per-paper citation counts from OpenAlex, in the same way again:

- `scripts/fetch-citations.ts` takes the DOIs of `data/publications.yml` (`doisFromPublications()` in `scripts/lib/openalex.ts`, normalised by `normalizeDoi()` — lowercase, no `https://doi.org/`/`doi:` prefix — unique and in file order; 87 of the 110 entries have one (86 unique DOIs; two entries share one)). `normalizeDoi()` itself lives in `site/lib/citationsSchema.ts` and is re-exported from `scripts/lib/openalex.ts`, so the writer of the snapshot and the page that looks entries up in it can never key it differently. The batches go to OpenAlex in groups of 50 (`filter=doi:<a>|<b>|…`, `select=id,doi,cited_by_count,open_access,counts_by_year`). No key: `OPENALEX_MAILTO` (a repository variable, unset by default) only adds the `mailto=` parameter of OpenAlex's polite pool, and the address is never hard-coded. The retry policy mirrors the GitHub client (3 attempts on 429/5xx/network, honouring `retry-after`); a 4xx is not retried.
- `per-page` is **200**, not the batch size: OpenAlex sometimes holds two work records for one DOI (a publisher version and a repository copy), so 50 DOIs can match more than 50 works and `per-page=50` silently dropped the overflow — `buildCitations()` keeps the more-cited record per DOI, and `fetchWorks()` warns when `meta.count` exceeds the number of returned results.
- `site/lib/citationsSchema.ts` is the single source of truth for the shape (`fetchedAt`, `works[<normalised doi>]` with `openalexId`, `citedByCount`, `isOa`, `oaStatus`, `countsByYear`), `.strict()` throughout, with `emptyCitations()` (epoch `fetchedAt`) as the fallback and `CITATIONS_URL` the raw URL on the `github-data` branch. The snapshot is keyed by the normalised DOI, so the publications page looks an entry up from its own `doi` field; a DOI OpenAlex does not know is **absent** rather than zero, and gets no badge. `openalexId` is constrained to `^W\d+$` by the schema — that is what makes it safe to interpolate into an `openalex.org` link; `oaStatus` is rendered as text, never as HTML.
- On `publications.astro` the snapshot is read once at build time (`site/lib/citations.ts`'s `loadCitations()`, same 10 s timeout / `emptyCitations()` fallback as the other two reads) and `citationFor(citations, pub.doi)` hands each row its entry. `PublicationRow.vue` renders, inside `.pub-links`, a `<span class="pub-cites" data-doi="<normalised doi>">` holding the "cited N" link (`<a data-field="cited">` to `https://openalex.org/<openalexId>`, `hidden` at zero or unknown) and the "open access" badge (`<span data-field="oa">`, no link, the `oaStatus` only in its `title`), plus `data-cited="<N>"` on the row. The skeleton is rendered for every row **with** a DOI even when the build had no snapshot, so `site/lib/citationsStats.ts` (`applyCitations`, `refreshNote`) can fill it in from `loadLiveCitations()` (`site/lib/citationsLive.ts`, memoized per page load) — text nodes, one `href` and `hidden` only, never HTML.
- The Year / Most cited toggle is `PublicationsOrder.astro`: static buttons (`#publication-order`, `data-order="year|cited"`, `.active`) plus a bundled script, not an island. `?order=cited` pre-applies, and `site/lib/pubOrder.ts` does the work — `orderByCitations()` **moves** the existing `tr[data-tags]` nodes into the flat table `#publication-list-flat` (by `data-cited` descending, ties by the remembered original position, i.e. year descending), hides the `.pub-year-group`s and shows the flat table; `restoreOrder()` puts every node back at the parent/next sibling a `WeakMap` remembers. There is never a second copy of a row. The flat table sits **inside** `#publication-list`, so `TagFilter` keeps finding the rows by `[data-tags]` in either order, and `restoreOrder()` re-derives each group's visibility the way the filter does, so a tag chosen while the list was flat still holds after switching back. A newer live snapshot re-runs the ordering when "Most cited" is active.
- `tests/fixtures/openalex/works.json` is a recorded response for four real DOIs — two older, well-cited papers, one 2026 paper and one DOI OpenAlex does not know, which is how the "missing" case is exercised.

```bash
npm run fetch:citations -- citations.json
```

The homepage's at-a-glance strip is the one consumer of these snapshots that does **not** refresh itself in the browser: `HomeStats.astro` reads the GitHub and Scholar snapshots at build time (`loadSnapshot()`/`loadScholar()`) and renders static markup with no `<script>`, no `client:` directive and no runtime fetch, so the homepage keeps shipping only the site chrome's JavaScript. What keeps its numbers current is the daily scheduled `site.yml` run (see "Branches and deployment"); a figure whose snapshot the build could not read (`hasData()` false, i.e. `emptyScholar()`/`emptySnapshot()`'s epoch `fetchedAt`) is left **out** of the strip rather than rendered as 0.

## UI conventions

- **Static-first islands**: list pages are plain HTML. One Vue SFC per entry type (`PublicationRow`, `ProjectCard`, `PersonCard`, `NewsCard`, `SoftwareCard`, `FundingCard`, `EditorCard`, `MeetingCard`, `PresentationCard`, `PosterCard`, `AbstractCard`, `TeachingCard`, …) is rendered from the `.astro` page **without** a `client:` directive, so no record is ever serialised a second time into `astro-island` props. Keep it that way: a new card belongs in the page's `.map()`, not in a wrapper island. Detail content is not on the list page at all any more — it is one prerendered fragment per entity, fetched into the shared detail modal (see below). Only the components below hydrate, and only these may take a `client:` directive:
  - `TagFilter.vue` (`client:idle`) — the tag filter bar on publications/projects/news/research/meetings.
  - `PersonAvatar.vue` (`client:visible`) — the hover cards on the homepage people strip and the alumni timeline.
  - `ReleaseFeed.vue`, `ReleaseTimeline.vue`, `CommitActivityChart.vue`, `StarsChart.vue` (`client:visible`, research page only) — the live GitHub sections: the feed is server-rendered and hydrates only to refresh itself, the three charts need a canvas (see "Live GitHub and Scholar data").
  - `CitationsPerYearChart.vue`, `CitationHistoryChart.vue` (`client:visible`, publications page only) — the two Google Scholar charts; both need a canvas and refresh themselves from the live snapshot (same section).
  - `PublicationsChart.vue` (`client:visible`, publications page only) — papers per year, stacked by research area or by status; a canvas again, but the rows come from the build (`site/lib/publicationRows.ts`, no snapshot and no refresh) and its Research area / Status buttons live **inside** the island because it is hydrated anyway (see "Publications over time" below).
  - `NetworkGraph.vue` (`client:load`, network page only) — the force-directed graph of `/network/`; the page's whole content, so it hydrates immediately rather than on visibility, and its research-area filter buttons live inside the island for the same reason as the one above (see "Network graph" below).

  Everything else that needs JavaScript is plain TypeScript in a bundled Astro `<script>` block (see "Site chrome" below), so a page without a list island — `/cv/`, `/teaching/`, `/impressum/`, `/privacy/`, `404` — ships no Vue runtime at all (8.6 KB of JS — the modal/detail router, the search dialog and the icon helper — instead of 82 KB).

  Anything rendered statically must not rely on `onMounted`/`onUnmounted`: they never run — every card SFC and `DetailView.vue` are pure templates. `panels`, `activities`, and `linkedin` have collections and schemas but no components or pages — nothing rendered them on the old site either; they feed the Python CV tooling only.
- **Tag filtering**: `data/tags.yml` defines the tag set (with per-tag icon/color); `TagList.vue` renders the badges and `TagFilterBar.vue` the buttons (`#<id>-tag-filter`, `data-tag`, `.active`) that `TagFilter.vue` wraps. `TagFilter` filters the *static DOM*: given `target` (the id of the container holding the cards/rows) it toggles the `hidden` attribute on every `[data-tags]` element inside it, and on every `groupSelector` wrapper (default `.pub-year-group`, the publications year groups) left with no visible item. `?tag=` pre-applies on mount and an unknown tag is ignored; `research.astro` mounts three of them over one `?tag=`. On the publications page the rows may have been moved into the flat "Most cited" table (`pubOrder.ts`, see above) — the filter is oblivious to that because the flat table lives inside the same `target` container. So a filterable card only needs `:data-tags="item.tags.join('|')"` and a container with an id — never an island. Visibility is the `hidden` attribute (Tailwind preflight's `[hidden]{display:none!important}`), never an inline `display`.
- **Publications over time**: `<section id="publications-chart">` on the publications page holds the `PublicationsChart.vue` island. `publicationsPerYear(publications, tags)` (`site/lib/publicationRows.ts`, pure and unit-tested) aggregates `data/publications.yml` in the page frontmatter into `{ years, byTag, byStatus }` — years contiguous from the first to the last publication year, a paper with several research areas counted once per area (the chart caption says so), every paper exactly once in the status split, all-zero series dropped. `publicationsOption(rows, mode)` in `site/lib/chartOptions.ts` stacks them; the research-area colours come from `TAG_PALETTE` there, which mirrors the `--color-tag-*` tokens of `global.css` by tag slug (`slugify(tag)`) — keep the two in sync — and the status colours are `PALETTE` indexed by `STATUS_ORDER`, so a status missing from the data does not shift the others. Clicks are wired in the component: a bar segment in research-area mode presses the matching `#publication-tag-filter [data-tag]` button (nothing happens if `TagFilter` has not hydrated yet) and scrolls to `#publication-list`; in status mode it only scrolls; a year label (`xAxis.triggerEvent`) scrolls to the `.pub-year-group` with that `h3.year-heading`, or to the list when the groups are hidden by "Most cited" order.
- **Homepage at-a-glance strip**: `HomeStats.astro` under the hero subtitle of `index.astro` — six `.home-stat` links (publications, citations, h-index, team, software, funded projects), each a big tabular number, a label and an optional muted second line. `homeFigures()` in `site/lib/homeStats.ts` (pure, unit-tested) builds the ordered list from `data/*.yml` plus the two build-time snapshots and decides what to omit; its `countPeerReviewed()` is the single definition of the site's publication count, shared with `ScholarStats.astro` on the publications page so the two figures cannot drift apart. Build-time only, see "Live GitHub and Scholar data" — the homepage must not gain a JS chunk for it. The `.home-stats` grid is `repeat(auto-fit, minmax(7.5em, 1fr))`, so it is one row of six on a wide screen and two columns on a phone without a media query.
- **Network graph**: the five research areas are **filters, not nodes** (user decision, see the amendment in the design spec), and only **people carry an image**. `graphRows()` in `site/lib/graphRows.ts` (pure and unit-tested, including tests over the real YAML: 209 nodes, 309 links) projects `data/{tags,people,publications,projects,software}.yml` into the `{ nodes, links }` of the graph — one node per person, publication, project and software row, ids `<type>:<data id>`, each node carrying its `label`, tooltip `detail`, `image` (a person's photo thumbnail, `null` for every other type), `topics` (the research-area slugs it is filtered by; a person's are the union of their publications' tags), `value` (its degree in the whole graph) and `citations` (a publication's count, for the tooltip; `null` elsewhere). Edges: publication → author, project/software → publication, person → project/software, deduplicated per node pair and only between existing nodes. Every `href` is built from the `base` input (`import.meta.env.BASE_URL`) and points at the item's list page plus its detail hash (`people/#person/<id>`, `projects/#project/<id>`, `research/#software/<id>`, `publications/#publication/<id>`), so an href opened directly lands on the list page with that modal open; adding or renaming one of those ids means changing it here too. The only thumbnails are the 61 people photos under `public/assets/image/graph/people/`, written by `npm run graph:thumbs` (`scripts/graph-thumbs.ts`, `sharp`; round, with a 2 px white ring) and committed; a person whose thumbnail is missing falls back to a circle, so a new person only gets a photo node after the script is re-run. `site/pages/network.astro` computes the rows in its frontmatter (the getters plus `loadCitations()` and the set of thumbnails that exist, read from `publicDir` with `node:fs` — `import.meta.url` would point into the bundled prerender chunk under `dist/`) and hands them to the one `NetworkGraph.vue` island (`client:load`, the page's whole content); its intro counts the *drawn* network (`filterRows(rows, null)`), "Network" is a top-level navbar entry (`sectionid="network"`) and every homepage research-area section links to `/network/?topic=<tag>`.

  `networkOption(rows, topic, { relayout })` in `site/lib/networkOptions.ts` (pure, unit-tested, reusing `PALETTE`/`TAG_PALETTE`/`tooltip()` from `chartOptions.ts`) builds the force-layout option over `filterRows(rows, slug)`: the nodes whose `topics` include the slug and the links between two of them (the whole graph for `null`), minus every node left **without a single link** — the view is always a network, which drops 23 people from the full graph. Node `id` is the row id (ECharts resolves a link's `source`/`target` against `id` before `name`, so `name` is free to be the human label); a person is their photo (`symbol: 'image://<url>'`, `symbolKeepAspect`), a project a `roundRect`, a software entry a `diamond` and a publication a circle in its first area's colour (`SYMBOL`), each in its category colour, which is also its legend swatch. Every node is sized by its **degree inside the drawn view** — `min + k·sqrt(degree)`, capped per type (`SIZE`, `symbolSize()`, `degrees()`) — so a filter re-sizes the graph; a publication's citation count only appears in its tooltip. `relayout` (the default) runs the force layout at `LAYOUT_FRICTION` with `initLayout: 'circular'`, which is what a filter change needs; `false` uses `SETTLE_FRICTION` (0), which cannot move a node, so a resize never reshuffles the graph. `useChart`'s `notMerge` accepts a predicate for exactly this: the component passes `() => relayout.value`, so a filter change is drawn from scratch (the layout re-arranges) and a resize merges (ECharts' `preservedPoints` keep every position). `zoom` is `ZOOM_ALL` 0.6 for the whole graph and `ZOOM_TOPIC` 1 for one area. `roam` is `ROAM` (`'move'`, so the wheel still scrolls the page) with `roamTrigger: 'global'` so a drag anywhere on the canvas pans; the zoom and reset buttons go through `roamChart()`/`resetChart()`, and `enableNodeDragging()` (all three in `useChart.ts`) switches roaming off while a node is dragged — without it ECharts' `RoamController` sees a non-draggable image element under the cursor and pans the view instead of moving the node. That `setOption` also rebuilds the series' graphic elements mid-press, so the chart never emits a `click` for a node: `enableNodeDragging()` owns the press/release pair and calls its `onNodeTap` callback when the pointer moved no more than 4 px between them, which is what opens the node's detail modal. The filter buttons are "All" plus the five areas (`.chart-mode-btn.network-topic-btn`, `.active`, `aria-pressed`), `?topic=` (tag name or slug, case-insensitive, unknown ignored) pre-selects one, the resize handler is debounced by 200 ms, and a node click opens that node's detail modal in place (`openDetail()`, the node id is already `<type>:<id>`), falling back to navigating to `data.href` — only when it starts with `import.meta.env.BASE_URL` — for a node type without a detail. The per-area artwork of the homepage sections is `TAG_GRAPHICS` in `site/lib/tagGraphics.ts`, keyed by tag slug, and so are the research-area colours (`TAG_PALETTE`, re-exported by `chartOptions.ts`).
- **Person hover cards**: hovering/focusing a `PersonAvatar.vue` (photo wrapped around a `PersonCard.vue` popup with name/position/description) shows a positioned info card, clamped to stay within the viewport. Reused by the homepage people strip and the Team page's alumni timeline — add new instances by reusing `PersonAvatar.vue` rather than duplicating the hover logic.
- **Person chips**: a different, inline pattern — `PersonChips.vue` splices a small avatar + bold name into free-text author/people strings (used on the publications and teaching pages), matching "Initial. Surname" first and falling back to "Given Surname".
- **Modal router**: native `<dialog class="modal">` elements, managed by one document-level router, `installModalRouter()` in `site/lib/modals.ts`, installed exactly once by the `<script>` at the end of `Base.astro`. It opens a static dialog from `data-modal-target="<dialog id>"` on a trigger (the site search is the only one left), closes on the backdrop, `[data-modal-close]` and Escape, and its initial/`hashchange` check scrolls to a `#anchor` and briefly highlights it (`#pub-<id>`, `#project-<id>`, … the list anchors search results and a detail's "Show in list" link point at). It also installs the **detail router** beside it (see below), which owns everything `[data-detail]` and every detail hash; the two cannot collide, because a detail hash never matches an element id.
- **The detail modal**: one shell for the whole site — `DetailModal.astro` (`<dialog id="detail-modal" class="modal detail-modal">` with a `.modal-back` button, an empty `.modal-title` and an empty `.modal-body`) sits in `Base.astro` on every page, and `site/lib/detailModal.ts` fills it with the prerendered fragment of the clicked entity. A trigger is any element with `data-detail="<type>:<id>"` (person cards and avatars, project and news cards, publication titles, software card titles, the related rows inside an open modal); a trigger that is also an anchor carries the matching `#<type>/<id>` href, so it deep-links and middle-clicks like a link, and a real link nested inside a clickable card still navigates on its own. `openDetail(type, id)` is the programmatic entry (the network graph calls it on a node click). The router fetches `${base}detail/<type>/<id>/` once per entity, parses it with `DOMParser` and **adopts** the `.detail` root into the dialog body — never a string as HTML — caching the node on the shell element, so a revisit is instant; `type` and `id` are validated against the five type names and `^[A-Za-z0-9_.-]+$` before any fetch. Addressing: `#<type>/<id>`, plus the legacy `#person-modal-<id>`/`#project-modal-<id>`/`#news-modal-<id>` of the retired per-page modals (`parseDetailHash()`); a click pushes that hash, a hash-driven open (load, `hashchange`, `popstate`) does not; a related row pushes onto an in-modal stack that the Back button pops, and a browser Back onto the entry below the top pops that stack instead of pushing the same detail again; closing drops the hash with `replaceState`, never `history.back()`, so the URL the reader is on stays in place and the first browser Back after using a modal stays on the page. A modified click (⌘/Ctrl/Shift/Alt or any non-primary button, `isModifiedClick()`) is never intercepted — by this router or by the `[data-modal-target]` one — so a trigger opens in a new tab like the link it is; and because replacing the body drops the focused related row, `render()` moves focus to the dialog's `.modal-title`. The per-page `PersonModal.vue`/`ProjectModal.vue`/`NewsModal.vue` and their per-page refs are gone — one shell replaces ~300 inline dialogs (the news page's HTML fell from 69 KB to 30 KB gzipped).
- **Standard detail (model, view, fragments)**: `site/lib/details.ts` is the single builder of the detail of a person, publication, project, software entry or news item (`DetailType`, the five node types of the network). `buildRelations(ctx)` derives the relations once and symmetrically from the data (a person is related to everything whose `people:` lists them; a publication to every project, software entry and presentation whose `publications:` lists it), `detailModel(type, id, ctx)` returns the `DetailModel` — header (image with its `imageShape`: `round` for a person, `logo` for a software entry, shown whole with `object-fit: contain` like on the research cards, `thumb` cropped to fill for the rest; title, one subtitle line, research areas, external links), figures (publication citations from the OpenAlex snapshot, software stats from the GitHub snapshot, a person's publication count and summed citations), media (one rich block between the figures and the body: a news item's YouTube embed as `{ kind: 'video' }`, a project's full image gallery with its `image_title` caption as `{ kind: 'gallery' }`, `null` for every other type — what the retired `NewsModal.vue`/`ProjectModal.vue` showed, which is also why a project carries no header thumbnail and a news item with a video no YouTube still), body (the data's own HTML), keywords, related sections and `listHref` — and `detailIds(ctx)` lists every entity that gets one. `listAnchor()` builds the list anchors (`people/#person-<id>`, `publications/#pub-<id>`, `projects/#project-<id>`, `research/#software-<id>`, `news/#news-<id>`, plus `publications/#presentation-<id>`/`#poster-<id>` for related presentation/poster rows). It is pure (no DOM, Vue or Astro imports) and builds every href from the `base` its `DetailContext` carries, like `graphRows.ts`. `site/components/DetailView.vue` renders one model — statically, never hydrated, so no lifecycle hooks — and `site/pages/detail/[type]/[id].astro` prerenders one fragment per entity at `/detail/<type>/<id>/` with `export const partial = true` (no doctype, no `<head>`, no layout: the response is the bare `<div class="detail">`), reading the collections and the three snapshots once in `getStaticPaths()`. The fragments are excluded from the sitemap in `astro.config.mjs` — they are modal content, not pages. Related rows of the five detail types carry `data-detail="<type>:<id>"` beside their list-anchor `href`. `DetailType`/`DETAIL_TYPES` live in the leaf module `site/lib/detailTypes.ts` (re-exported by `details.ts`): the browser-side router and the network island need the names, and importing them from `details.ts` would drag the whole build-time model — YAML, Zod, snapshots — into the site chrome bundle.
- **Links and assets**: every internal link and static-asset reference goes through `url()`/`asset()` in `site/lib/url.ts` so it carries the deploy's base path (`import.meta.env.BASE_URL`, `/` locally, `/livermetabolism-site/` on the interim GitHub Pages URL) — never hand-write a root-relative `href`/`src`.
- **Icons**: `site/icons/*.svg` (Font Awesome 4 names, fetched by `scripts/fetch-icons.sh`), rendered via `<Icon name="globe" />` (`site/components/Icon.vue`, backed by `site/lib/icons.ts`), inlined at build time with the old `fa fa-<name>` classes so the ported CSS keeps matching.
- **Styling**: `site/styles/global.css` — a Tailwind v4 `@theme` plus the hand-ported site rules, layered as `@layer theme, base, components, utilities, overrides;`. No CSS-framework classes beyond what's explicitly re-created (`btn*`, `container`, `modal*`, `navbar*`, …); notably `.container` lives in the `overrides` layer because Tailwind's own built-in `.container` utility would otherwise win and conflict with the site's.
- **Site search**: `site/pages/search.json.ts` builds a JSON index of every `data/*.yml` table plus the static pages at build time; add a new table there if it should be searchable. `SiteSearch.astro` (opened via the navbar icon, `/`, or Cmd/Ctrl+K) fetches that index the first time the dialog opens, scores/filters it client-side with `rankRecords()` from `site/lib/search.ts`, and deep-links into the routers above — a person, publication, project, software or news record points at `<list page>#<type>/<id>` (the detail modal, opened on arrival or, on the same page, by the `hashchange`), everything else at its list anchor. Its result rows are built with `createElement`/`textContent` — never by interpolating a record field into an HTML string; the only markup inserted as HTML is `iconSvg()`'s allow-listed sprite reference.
- **Site chrome**: the navbar toggle (`TopNav.astro`), the cookie banner (`CookieConsent.astro`), the search dialog (`SiteSearch.astro`), and the modal router (`Base.astro`) are on every page, so none of them is a Vue island: each is static markup plus a bundled Astro `<script>` block (TypeScript, hashed for the CSP, deduplicated per page, runs once after parse) that imports the shared logic from `site/lib/*.ts`. Configuration reaches those scripts through `data-*` attributes on the component's root element (`data-ga-id`, `data-search-url`), never through props. Never write the literal text `<script>` (or `<style>`) in a comment inside an `.astro` file's frontmatter or template: Vite's dependency scanner extracts script blocks from `.astro` files with a regex, trips over it, aborts the whole scan ("Failed to run dependency scan"), and the dev server then answers first loads with `504 Outdated Optimize Dep` while it re-optimises dependencies one by one. Keep new chrome that way; `client:` directives are for the islands listed above. `SoftwareLive.astro` (research page only) follows the same pattern for the live GitHub stats lines.
- **robots.txt and LLM files**: `site/pages/robots.txt.ts`, `llms.txt.ts` and `llms-full.txt.ts` are build-time endpoints over the pure builders `robotsTxt()`, `llmsTxt()` and `llmsFullTxt()` in `site/lib/llms.ts` (unit-tested, including over the real YAML). `robots.txt` lets every crawler in — AI crawlers included, a user decision — except `/detail/` (the modal fragments, also kept out of the sitemap) and names `sitemap-index.xml` and both LLM files; `llms.txt` is the https://llmstxt.org/ index (H1, blockquote summary, link lists, `## Optional` last), `llms-full.txt` the content of every list page as one Markdown file, showing only what the site shows (current projects, current members plus alumni with a photo). Every link is absolute, built from the endpoint's `site` and `BASE_URL`, and data HTML goes through `plainText()` (links become Markdown links, never markup). A new table the site shows needs a section in `llmsFullTxt()` as well as in `search.json.ts`; the static page list both use is `SITE_PAGES` in `site/lib/sitePages.ts`.
- **Web manifest**: `site/pages/site.webmanifest.ts` is an Astro endpoint (route derived from the file name, like `search.json.ts` -> `/search.json`) rather than a static file under `public/`, so its `icons[].src` values go through `asset()` and carry the deploy's base path; `Head.astro` links `url('/site.webmanifest')`.

## Notable conventions

- Publication entries have a `status` field (`thesis`, `report`, `preprint`, `publication`, `review`, `proceeding`, `chapter`, `abstract`) and a `position` field (`first`, `first_equal`, `index`, `last_equal`, `last`) that drive both the publications page and the Typst generation logic in `src/cv/list_of_publications.py`; both are enums in `src/data.py`'s `Publication` model (and in `site/lib/schemas.ts`'s Zod equivalent). On the site, `status` also selects the `.status-{status}` badge style in `global.css` (`publication` is the solid/prominent one; the rest are muted outline pills).
- `pdf`/`image` fields in `data/*.yml` (e.g. `publications.yml`, `posters.yml`) are paths relative to `public/assets/pdf/`, including the status subfolder (e.g. `'publication/Foo2026_bar.pdf'` → `public/assets/pdf/publication/Foo2026_bar.pdf`); Typst generators build the live PDF link as `https://livermetabolism.com/assets/pdf/{e.pdf}`, and the site does the equivalent via `asset()`.
- Google Analytics only loads after cookie-consent opt-in (`CookieConsent.astro`, gated by the `gaId` prop `site/layouts/Base.astro` passes it and forwards to its script as `data-ga-id`; `/privacy/`'s `#cookie-consent-reset` button withdraws consent and brings the banner back) — never add another third-party/tracking script unconditionally; gate it the same way. `site/pages/impressum.astro`/`privacy.astro` document what's actually collected, so update them if that changes.
- **Content-Security-Policy**: `astro.config.mjs`'s `security.csp` renders a per-page `<meta http-equiv="content-security-policy">`; Astro hashes its own bundled/inline scripts and styles (the `<script>` blocks of the site chrome and the Vue island hydration runtime alike) automatically, so only third-party hosts need to be listed in `directives`/`scriptDirective.resources`/`styleDirective.resources` by hand — add any new one there. Neither directive needs `'unsafe-inline'`: CSP's `style-src` only governs `<style>` elements and `style=` attributes (never CSSOM writes like `PersonAvatar.vue`'s runtime `el.style.transform = ...`, which it doesn't restrict at all), and any real `style=` attribute instead gets its own class in `site/styles/global.css` (e.g. `cv.astro`'s `.cv-pdf-embed`); `script-src` must never get `'unsafe-inline'` either.
- **GitHub Pages size caveat**: `public/assets/pdf` is about 871 MB, against GitHub Pages' 1 GB per-site limit — be mindful of this when adding large PDFs (posters, theses).

## Branches and deployment

`main` is protected by a repository ruleset (pull requests only, linear history, squash or rebase merges, required status checks `validate` and `build`); there is no `develop` branch — work on a topic branch and open a PR against `main`. `.github/workflows/site.yml` runs on every push and PR, plus daily at 06:00 UTC (`schedule`, one hour after the data workflow, so the build-time numbers of the live snapshots are never more than a day old; the `deploy` condition — not a pull request, `refs/heads/main` — covers a scheduled run, which always uses the default branch): `validate` (Python: pytest + `src.data`), then `build` (Node: `astro check`, vitest, `astro build`, Playwright e2e against the built site), then — only on a push to `main`, not on a PR — `deploy`, which publishes `dist/` to GitHub Pages via `actions/deploy-pages`. The build currently targets the interim project-pages URL (`SITE=https://matthiaskoenig.github.io`, `BASE=/livermetabolism-site/`); switching to the custom domain means changing those two env vars to `SITE=https://livermetabolism.com`/`BASE=/`, adding `public/CNAME`, and configuring the domain in the repository's Pages settings.

Releases are cut from `main`: bump `package.json` and `pyproject.toml` to the new version (then `npm install --package-lock-only` and `uv lock` so both lockfiles record it), add `release-notes/<version>.md`, merge that through a PR, then `git tag <version> && git push origin <version>` — tags carry no `v` prefix. `.github/workflows/release.yml` fires on such a tag, verifies it matches both version fields and that the notes file exists, and creates the GitHub release from those notes.

`astro.config.mjs` injects the `package.json` version and the build's commit (`SITE_COMMIT`, else `GITHUB_SHA`, else `git rev-parse HEAD`, else `'unknown'`) as the `__SITE_VERSION__`/`__SITE_COMMIT__` Vite defines (declared in `site/env.d.ts`), which `Footer.astro` renders as links to the release and the commit. The `node:24-alpine` build container has no git, so `deploy.sh` exports `SITE_COMMIT` and `docker-compose-build.yml` forwards it; GitHub Actions needs nothing.

Two deployment paths exist and must both keep working: GitHub Pages (`.github/workflows/site.yml`, base path `/livermetabolism-site/` until the domain moves) and the self-hosted nginx container (`docker-compose.yml` serves `dist/` built by `docker-compose-build.yml` with `SITE=https://livermetabolism.com`, `BASE=/`; `deploy.sh` runs both on the server; `nginx/` holds the container config plus the host reverse-proxy/SSL configs). `docker-compose-serve.yml` is the containerised `npm run dev`. `dist/` is gitignored and built on the server.
