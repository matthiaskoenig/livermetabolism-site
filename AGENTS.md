# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Static site source for the König research group site (https://www.livermetabolism.com/), built with [Astro](https://astro.build/) (static output), [Vue](https://vuejs.org/) components (statically rendered, with a handful of small hydrated islands), and plain TypeScript for the site chrome, styled with Tailwind v4. A small Python/uv package under `src/` generates Typst-formatted content (publication lists, CV, funding, presentations, etc.) from the same YAML data used by the Astro site. That YAML data has a pydantic schema (`src/data.py`) mirrored by a Zod schema (`site/lib/schemas.ts`) — see "Data model & validation" below before editing `data/*.yml` by hand.

## Repository layout

Only what `ls` does not tell you:

- `site/` is the Astro app - Astro's default `src/` is taken by the Python package. Pages that exist in both languages sit under `pages/[...locale]/`; `404.astro`, `robots.txt.ts`, `llms.txt.ts`, `llms-full.txt.ts` and `site.webmanifest.ts` sit directly under `pages/` because they are single, locale-independent files. Unit tests are co-located (`site/**/*.test.ts`, `scripts/**/*.test.ts`).
- `data/` is the single database and the English source; it is validated twice (`src/data.py`, `site/lib/schemas.ts`) - keep the two schemas in sync when adding a field.
- `public/assets/image/graph/` and the 128 px avatars are committed generator output (`npm run graph:thumbs`, the only use of `sharp`), never built on the fly. `assets_src/` holds raster masters that are not served.
- `src/` is a standalone Python package, not part of the Astro build. Generators under `src/cv/` run as modules (`uv run python -m src.cv.list_of_publications`), not via a CLI entrypoint; edit the `selected`/`highlights` sets at the bottom of a script to change its output. Not every `data/*.yml` file has a generator.
- `scripts/` is run directly by Node 24 with no build step, so imports inside `scripts/` and into `site/lib/` carry the `.ts` extension. Its tests run under the same vitest config as `site/`; the recorded API responses they use live in `tests/fixtures/{github,scholar,openalex}/`.
- `scripts/fetch-icons.sh` names the Font Awesome Free 6 SVGs in `site/icons/` by the Font Awesome 4 class names that `data/tags.yml` keeps. `scripts/reindent_yaml.py` fixes the YAML indentation rule below.
- `science_communication/` is planning notes, not part of the build.

## Data model & validation

`src/data.py` defines a pydantic model for every table in `data/*.yml`, and cross-validates the relationships between them: `people: list[str]` fields (on publications/projects/software/news/teaching/presentations/posters/panels/abstracts) must resolve to real `people.yml` ids, `tags: list[str]` must be tags defined in `tags.yml`, `publications: list[str]` (on projects/software/presentations/panels) must resolve to real `publications.yml` ids, ids must be unique within their table, and referenced image/pdf files must exist under `public/assets/image/`/`public/assets/pdf/` — including `publications.pdf` and `funding.funder_logo` (see `IMAGE_FIELDS` in `src/data.py`).

After **any** manual edit to `data/*.yml`, run:
```bash
uv run python -m src.data
```
This loads and validates all of it, printing every problem found (not just the first) and exiting non-zero on failure — the same check `tests/test_real_data.py` runs in CI, so a bad edit fails the build before merge rather than silently breaking the live site.

`js-yaml` (the parser the Astro build uses) follows YAML 1.2, which requires the continuation lines of a multi-line quoted string to be indented **deeper than their key** — PyYAML accepts them flush with the key, `js-yaml` rejects the file with "deficient indentation". Keep new multi-line values indented, or run `uv run python scripts/reindent_yaml.py` (`--check` reports without writing), which re-indents only those continuation lines and refuses to write if `yaml.safe_load()` no longer returns the same object.

The Astro build re-validates the same YAML independently through `site/lib/schemas.ts` (Zod schemas wired into `content.config.ts`'s collection loaders) and fails the build on a dangling `people`/`tags`/`publications` reference — the two schemas must be kept in sync by hand when a field is added or changed.

Astro's content layer does **not** preserve a YAML file's row order (it persists collections sorted alphabetically by id for deterministic build caching). The `yml()` loader in `content.config.ts` injects an `order` field recording each row's original position; `all()` in `site/lib/data.ts` sorts by it and strips it back out before returning, and `getTags()` goes through `toTagInfo()` in `site/lib/views.ts` to do the same for tags. Any new collection that cares about display order must go through `yml()`/`all()` rather than calling `getCollection()` directly.

`site/lib/data.ts`'s `all<K extends keyof CollectionData>(key: K)` infers its return type from `key` alone via a `CollectionData` interface mapping every collection it serves to its schema type — add a new collection there (not as a caller-supplied generic) when adding a `get*()` wrapper.

Field names are unified across tables for the same concept: `people` is always the internal-person-id list (as opposed to `authors`, the free-text bibliographic string with affiliations/superscripts); `tags` always references `tags.yml`; `homepage` is always "this thing's own/associated external URL" (not `project`); `event`/`event_page` is always the conference/meeting a talk/poster/abstract belongs to (not `meeting`/`webpage`); `tenure` is always a free-text period range like `"2020-2025"` (not `year`/`term`, which were ambiguous with the single-year `int` used on bibliographic entries); `role` is a person's list of positions held (not `position`, which on `Publication` means author-order instead). Country flags are looked up from `country_flags.yml` by `person.country` rather than stored per-person.

## Live GitHub and Scholar data

Three live snapshots (`github.json`, `scholar.json`, `citations.json`) feed the research, publications and home pages. The full contract is in `.claude/rules/live-snapshots.md`, which loads when you work on `scripts/`, the snapshot readers in `site/lib/` or the components that render them. What must hold everywhere:

- The snapshots live only on the orphan branch `github-data`. Never delete `scholar.json` there - its citation history exists nowhere else.
- `site.yml` runs only on `main` and pull requests, so a push to `github-data` never triggers a build or deploy - keep it that way.
- The snapshots carry text only. Never insert snapshot content as HTML, and never let a snapshot string become an `href` the page did not build itself.
- The snapshots bypass the Astro data pipeline (one build-time read plus a browser refresh), so the pages stay current without a redeploy. A failed read falls back to an empty snapshot: it must never fail the build, and a missing figure is left out or hidden, never rendered as 0.
- Each snapshot has one `.strict()` schema in `site/lib/*Schema.ts` shared by its writer and every reader - change the shape there, nowhere else.

## UI conventions

- **Static-first islands**: list pages are plain HTML. One Vue SFC per entry type (`PublicationRow`, `ProjectCard`, `PersonCard`, `NewsCard`, `SoftwareCard`, `FundingCard`, `EditorCard`, `MeetingCard`, `PresentationCard`, `PosterCard`, `AbstractCard`, `TeachingCard`, …) is rendered from the `.astro` page **without** a `client:` directive, so no record is ever serialised a second time into `astro-island` props. Keep it that way: a new card belongs in the page's `.map()`, not in a wrapper island. Detail content is not on the list page at all any more — it is one prerendered fragment per entity, fetched into the shared detail modal (see below). Only the components below hydrate, and only these may take a `client:` directive:
  - `TagFilter.vue` (`client:idle`) — the tag filter bar on publications/projects/news/research/meetings.
  - `PersonAvatar.vue` (`client:visible`) — the hover cards on the homepage people strip and the alumni timeline.
  - `ReleaseFeed.vue`, `ReleaseTimeline.vue`, `CommitActivityChart.vue`, `StarsChart.vue` (`client:visible`, research page only) — the live GitHub sections: the feed is server-rendered and hydrates only to refresh itself, the three charts need a canvas (see "Live GitHub and Scholar data").
  - `CitationsPerYearChart.vue`, `CitationHistoryChart.vue` (`client:visible`, publications page only) — the two Google Scholar charts; both need a canvas and refresh themselves from the live snapshot (same section).
  - `PublicationsChart.vue` (`client:visible`, publications page only) — papers per year, stacked by research area or by status; a canvas again, but the rows come from the build (`site/lib/publicationRows.ts`, no snapshot and no refresh) and its Research area / Status buttons live **inside** the island because it is hydrated anyway (see "Publications over time" below).
  - `NetworkGraph.vue` (`client:load`, network page only) — the force-directed graph of `/network/`; the page's whole content, so it hydrates immediately rather than on visibility, and its research-area filter buttons live inside the island for the same reason as the one above (see "Network graph" below).

  Everything else that needs JavaScript is plain TypeScript in a bundled Astro `<script>` block (see "Site chrome" below), so a page without a list island — `/cv/`, `/teaching/`, `/impressum/`, `/privacy/`, `404` — ships no Vue runtime at all (8.6 KB of JS — the modal/detail router, the search dialog and the icon helper — instead of 82 KB).

  Anything rendered statically must not rely on `onMounted`/`onUnmounted`: they never run — every card SFC and `DetailView.vue` are pure templates. `panels`, `activities`, and `linkedin` have collections and schemas but no components or pages — nothing rendered them on the old site either; they feed the Python CV tooling only.
- **Tag filtering**: `data/tags.yml` defines the tag set (with per-tag icon/color); `TagList.vue` renders the badges and `TagFilterBar.vue` the buttons (`#<id>-tag-filter`, `data-tag`, `.active`) that `TagFilter.vue` wraps. `TagFilter` filters the *static DOM*: given `target` (the id of the container holding the cards/rows) it toggles the `hidden` attribute on every `[data-tags]` element inside it, and on every `groupSelector` wrapper (default `.pub-year-group`, the publications year groups) left with no visible item. `?tag=` pre-applies on mount and an unknown tag is ignored; `research.astro` mounts three of them over one `?tag=`. On the publications page the rows may have been moved into the flat "Most cited" table (`pubOrder.ts`, see above) — the filter is oblivious to that because the flat table lives inside the same `target` container. So a filterable card only needs `:data-tags="item.tags.join('|')"` and a container with an id — never an island. Visibility is the `hidden` attribute (Tailwind preflight's `[hidden]{display:none!important}`), never an inline `display`.
- **Publications over time**: `<section id="publications-chart">` on the publications page holds the `PublicationsChart.vue` island. `publicationsPerYear(publications, tags)` (`site/lib/publicationRows.ts`, pure and unit-tested) aggregates `data/publications.yml` in the page frontmatter into `{ years, byTag, byStatus }` — years contiguous from the first to the last publication year, a paper with several research areas counted once per area (the chart caption says so), every paper exactly once in the status split, all-zero series dropped. `publicationsOption(rows, mode)` in `site/lib/chartOptions.ts` stacks them; the research-area colours come from `TAG_PALETTE` there, which mirrors the `--color-tag-*` tokens of `global.css` by tag slug (`slugify(tag)`) — keep the two in sync — and the status colours are `PALETTE` indexed by `STATUS_ORDER`, so a status missing from the data does not shift the others. Clicks are wired in the component: a bar segment in research-area mode presses the matching `#publication-tag-filter [data-tag]` button (nothing happens if `TagFilter` has not hydrated yet) and scrolls to `#publication-list`; in status mode it only scrolls; a year label (`xAxis.triggerEvent`) scrolls to the `.pub-year-group` with that `h3.year-heading`, or to the list when the groups are hidden by "Most cited" order.
- **Homepage at-a-glance strip**: `HomeStats.astro` under the hero subtitle of `index.astro` — six `.home-stat` links (publications, citations, h-index, team, software, funded projects), each a big tabular number, a label and an optional muted second line. `homeFigures()` in `site/lib/homeStats.ts` (pure, unit-tested) builds the ordered list from `data/*.yml` plus the two build-time snapshots and decides what to omit; its `countPeerReviewed()` is the single definition of the site's publication count, shared with `ScholarStats.astro` on the publications page so the two figures cannot drift apart. Build-time only, see "Live GitHub and Scholar data" — the homepage must not gain a JS chunk for it. The `.home-stats` grid is `repeat(auto-fit, minmax(7.5em, 1fr))`, so it is one row of six on a wide screen and two columns on a phone without a media query.
- **Network graph**: the five research areas are **filters, not nodes** (user decision, see the amendment in the design spec), and only **people carry an image**. `graphRows()` in `site/lib/graphRows.ts` builds every node `href` as the item's list page plus its detail hash, so adding or renaming a detail id means changing it there too, and a new person only gets a photo node after `npm run graph:thumbs` is re-run. Everything else (projection, layout, sizing, roaming, node dragging, filters) is in `.claude/rules/network-graph.md`, which loads with the graph's files.
- **Person hover cards**: hovering/focusing a `PersonAvatar.vue` (photo wrapped around a `PersonCard.vue` popup with name/position/description) shows a positioned info card, clamped to stay within the viewport. Reused by the homepage people strip and the Team page's alumni timeline — add new instances by reusing `PersonAvatar.vue` rather than duplicating the hover logic.
- **Person chips**: a different, inline pattern — `PersonChips.vue` splices a small avatar + bold name into free-text author/people strings (used on the publications and teaching pages), matching "Initial. Surname" first and falling back to "Given Surname".
- **Modal router and the detail modal**: one document-level router (`installModalRouter()` in `site/lib/modals.ts`, installed exactly once by `Base.astro`) and one shared shell (`DetailModal.astro`, filled by `site/lib/detailModal.ts` with the prerendered fragment `/detail/<type>/<id>/`). A trigger is any element with `data-detail="<type>:<id>"`; `openDetail(type, id)` is the programmatic entry. A fragment is adopted as a DOM node - never inserted as an HTML string - and `site/lib/details.ts` is the single builder of every detail model. Browser code imports `DetailType`/`DETAIL_TYPES` from the leaf module `site/lib/detailTypes.ts`: importing them from `details.ts` drags the whole build-time model into the site chrome bundle. The full contract (addressing, history, focus, model fields, fragments) is in `.claude/rules/detail-modal.md`, which loads with those files.
- **Links and assets**: every internal link and static-asset reference goes through `url()`/`asset()` in `site/lib/url.ts` so it carries the deploy's base path (`import.meta.env.BASE_URL`, `/` locally, `/livermetabolism-site/` on the interim GitHub Pages URL) — never hand-write a root-relative `href`/`src`.
- **Icons**: `site/icons/*.svg` (Font Awesome 4 names, fetched by `scripts/fetch-icons.sh`), rendered via `<Icon name="globe" />` (`site/components/Icon.vue`, backed by `site/lib/icons.ts`), inlined at build time with the old `fa fa-<name>` classes so the ported CSS keeps matching.
- **Styling**: `site/styles/global.css` — a Tailwind v4 `@theme` plus the hand-ported site rules, layered as `@layer theme, base, components, utilities, overrides;`. No CSS-framework classes beyond what's explicitly re-created (`btn*`, `container`, `modal*`, `navbar*`, …); notably `.container` lives in the `overrides` layer because Tailwind's own built-in `.container` utility would otherwise win and conflict with the site's.
- **Site search**: `site/pages/[...locale]/search.json.ts` builds, per locale, a JSON index of every `data/*.yml` table plus the static pages at build time; add a new table there if it should be searchable. `SiteSearch.astro` (opened via the navbar icon, `/`, or Cmd/Ctrl+K) fetches that index the first time the dialog opens, scores/filters it client-side with `rankRecords()` from `site/lib/search.ts`, and deep-links into the routers above — a person, publication, project, software or news record points at `<list page>#<type>/<id>` (the detail modal, opened on arrival or, on the same page, by the `hashchange`), everything else at its list anchor. Its result rows are built with `createElement`/`textContent` — never by interpolating a record field into an HTML string; the only markup inserted as HTML is `iconSvg()`'s allow-listed sprite reference.
- **Site chrome**: the navbar toggle (`TopNav.astro`), the cookie banner (`CookieConsent.astro`), the search dialog (`SiteSearch.astro`), and the modal router (`Base.astro`) are on every page, so none of them is a Vue island: each is static markup plus a bundled Astro `<script>` block (TypeScript, hashed for the CSP, deduplicated per page, runs once after parse) that imports the shared logic from `site/lib/*.ts`. Configuration reaches those scripts through `data-*` attributes on the component's root element (`data-ga-id`, `data-search-url`), never through props. Never write the literal text `<script>` (or `<style>`) in a comment inside an `.astro` file's frontmatter or template: Vite's dependency scanner extracts script blocks from `.astro` files with a regex, trips over it, aborts the whole scan ("Failed to run dependency scan"), and the dev server then answers first loads with `504 Outdated Optimize Dep` while it re-optimises dependencies one by one. Keep new chrome that way; `client:` directives are for the islands listed above. `SoftwareLive.astro` (research page only) follows the same pattern for the live GitHub stats lines.
- **robots.txt and LLM files**: `site/pages/robots.txt.ts`, `llms.txt.ts` and `llms-full.txt.ts` are single, locale-independent build-time endpoints (outside `pages/[...locale]/`, see "Internationalization (i18n)" below) over the pure builders `robotsTxt()`, `llmsTxt()` and `llmsFullTxt()` in `site/lib/llms.ts` (unit-tested, including over the real YAML). `robots.txt` lets every crawler in — AI crawlers included, a user decision — except `/detail/` and `/de/detail/` (the modal fragments of both locales, also kept out of the sitemap) and names `sitemap-index.xml` and both LLM files; `llms.txt` is the https://llmstxt.org/ index (H1, blockquote summary, link lists, `## Optional` last), staying a single mostly-English index that links both language homepages and both halves of `llms-full.txt`; `llms-full.txt` is the content of every list page as **one bilingual Markdown file** — the English document, then a German half after a `## Deutsch` heading (a deliberate choice, task 19: one file an agent can fetch once and find either language in, not per-locale files) — showing only what the site shows (current projects, current members plus alumni with a photo). Every link is absolute, built from the endpoint's `site` and `BASE_URL`, and data HTML goes through `plainText()` (links become Markdown links, never markup). A new table the site shows needs a section in `llmsFullTxt()` as well as in `search.json.ts`; the static page list both use is `SITE_PAGES` in `site/lib/sitePages.ts`.
- **Web manifest**: `site/pages/site.webmanifest.ts` is an Astro endpoint (route derived from the file name, like `search.json.ts` -> `/search.json`) rather than a static file under `public/`, so its `icons[].src` values go through `asset()` and carry the deploy's base path; `Head.astro` links `url('/site.webmanifest')`.

## Internationalization (i18n)

The site is English (default, unprefixed) and German (`/de/`). The full contract (routing, data and UI catalogs, drift guard, tag labels, the two language switches) is in `.claude/rules/i18n.md`, which loads when you work on `i18n/`, `site/lib/i18n/` or the i18n scripts; `i18n/TRANSLATION.md` is the translation guide. What must hold everywhere:

- `data/*.yml` and `site/lib/i18n/ui.en.ts` are the English source. Never hand-edit `i18n/de/*.yml` or `i18n/de/ui.yml` - regenerate them with the `translate-de` skill, then run `npm run i18n:check` until clean.
- The legal pages invert the direction: `i18n/de/pages/impressum.yml`/`privacy.yml` are the German source (the legally binding text), and `i18n/en/pages/` is generated from them.
- Never hand-write a `/de/...` href - go through `localeUrl()`/`urlFor()`/`switchPath()` in `site/lib/i18n/routes.ts`, and give every page under `pages/[...locale]/` `localePaths()` as its `getStaticPaths`.
- A new chrome string goes into `ui.en.ts` (the build throws if the German key set does not match exactly); a new translatable data field must be registered in `TRANSLATABLE` (`site/lib/i18n/fields.ts`).
- A tag's reference value (`tags.tag`) is never translated - it is a slug source, a filter value and a chart series key; only its display label (`TagInfo.label`) is.

```bash

# Under an AI-agent environment (e.g. Claude Code) `astro preview` backgrounds itself,
```

```bash
uv sync

```
Generator scripts live under `src/cv/` and cross-import each other (e.g. `from src.cv.list_of_software import read_data`), so run them with `-m src.cv.<script>` from the repo root rather than invoking the file directly.
```bash
uv run python -m src.data
uv run pytest tests/
```

## Notable conventions

- Publication entries have a `status` field (`thesis`, `report`, `preprint`, `publication`, `review`, `proceeding`, `chapter`, `abstract`) and a `position` field (`first`, `first_equal`, `index`, `last_equal`, `last`) that drive both the publications page and the Typst generation logic in `src/cv/list_of_publications.py`; both are enums in `src/data.py`'s `Publication` model (and in `site/lib/schemas.ts`'s Zod equivalent). On the site, `status` also selects the `.status-{status}` badge style in `global.css` (`publication` is the solid/prominent one; the rest are muted outline pills).
- `pdf`/`image` fields in `data/*.yml` (e.g. `publications.yml`, `posters.yml`) are paths relative to `public/assets/pdf/`, including the status subfolder (e.g. `'publication/Foo2026_bar.pdf'` → `public/assets/pdf/publication/Foo2026_bar.pdf`); Typst generators build the live PDF link as `https://livermetabolism.com/assets/pdf/{e.pdf}`, and the site does the equivalent via `asset()`.
- Google Analytics only loads after cookie-consent opt-in (`CookieConsent.astro`, gated by the `gaId` prop `site/layouts/Base.astro` passes it and forwards to its script as `data-ga-id`; `/privacy/`'s `#cookie-consent-reset` button withdraws consent and brings the banner back) — never add another third-party/tracking script unconditionally; gate it the same way. `site/pages/[...locale]/impressum.astro`/`privacy.astro` document what's actually collected, so update them if that changes (in German - see "Internationalization (i18n)", the legal pages invert the usual translation direction).
- **Content-Security-Policy**: `astro.config.mjs`'s `security.csp` renders a per-page `<meta http-equiv="content-security-policy">`; Astro hashes its own bundled/inline scripts and styles (the `<script>` blocks of the site chrome and the Vue island hydration runtime alike) automatically, so only third-party hosts need to be listed in `directives`/`scriptDirective.resources`/`styleDirective.resources` by hand — add any new one there. Neither directive needs `'unsafe-inline'`: CSP's `style-src` only governs `<style>` elements and `style=` attributes (never CSSOM writes like `PersonAvatar.vue`'s runtime `el.style.transform = ...`, which it doesn't restrict at all), and any real `style=` attribute instead gets its own class in `site/styles/global.css` (e.g. `cv.astro`'s `.cv-pdf-embed`); `script-src` must never get `'unsafe-inline'` either.
- **GitHub Pages size caveat**: `public/assets/pdf` is about 871 MB, against GitHub Pages' 1 GB per-site limit — be mindful of this when adding large PDFs (posters, theses).

## Branches and deployment

`main` is protected by a repository ruleset (pull requests only, linear history, squash or rebase merges, required status checks `validate` and `build`); there is no `develop` branch — work on a topic branch and open a PR against `main`. `.github/workflows/site.yml` runs on every push and PR, plus daily at 06:00 UTC (`schedule`, one hour after the data workflow, so the build-time numbers of the live snapshots are never more than a day old; the `deploy` condition — not a pull request, `refs/heads/main` — covers a scheduled run, which always uses the default branch): `validate` (Python: pytest + `src.data`), then `build` (Node: `astro check`, vitest, `astro build`, Playwright e2e against the built site), then — only on a push to `main`, not on a PR — `deploy`, which publishes `dist/` to GitHub Pages via `actions/deploy-pages`. The build currently targets the interim project-pages URL (`SITE=https://matthiaskoenig.github.io`, `BASE=/livermetabolism-site/`); switching to the custom domain means changing those two env vars to `SITE=https://livermetabolism.com`/`BASE=/`, adding `public/CNAME`, and configuring the domain in the repository's Pages settings.

Releases are cut from `main`: bump `package.json` and `pyproject.toml` to the new version (then `npm install --package-lock-only` and `uv lock` so both lockfiles record it), add `release-notes/<version>.md`, merge that through a PR, then `git tag <version> && git push origin <version>` — tags carry no `v` prefix. `.github/workflows/release.yml` fires on such a tag, verifies it matches both version fields and that the notes file exists, and creates the GitHub release from those notes.

`astro.config.mjs` injects the `package.json` version and the build's commit (`SITE_COMMIT`, else `GITHUB_SHA`, else `git rev-parse HEAD`, else `'unknown'`) as the `__SITE_VERSION__`/`__SITE_COMMIT__` Vite defines (declared in `site/env.d.ts`), which `Footer.astro` renders as links to the release and the commit. The `node:24-alpine` build container has no git, so `deploy.sh` exports `SITE_COMMIT` and `docker-compose-build.yml` forwards it; GitHub Actions needs nothing.

Two deployment paths exist and must both keep working: GitHub Pages (`.github/workflows/site.yml`, base path `/livermetabolism-site/` until the domain moves) and the self-hosted nginx container (`docker-compose.yml` serves `dist/` built by `docker-compose-build.yml` with `SITE=https://livermetabolism.com`, `BASE=/`; `deploy.sh` runs both on the server; `nginx/` holds the container config plus the host reverse-proxy/SSL configs). `docker-compose-serve.yml` is the containerised `npm run dev`. `dist/` is gitignored and built on the server.
