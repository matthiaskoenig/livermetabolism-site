# Code and security review - 2026-09-15

## Scope and result

Reviewed the static Astro/Vue site, snapshot readers and writers, content schemas,
Python generators, GitHub workflows, nginx configuration, and deployment scripts.
Reproduced browser defects against a local production build before applying fixes.
This is a source/configuration review and local browser evaluation, not a penetration
test of the production host. No deployment or remote repository changes were made.

## Fixed in this working tree

### 1. Consent withdrawal did not stop Analytics (high privacy impact)

Files: `site/lib/consent.ts`, `site/components/CookieConsent.astro`.

Accepting Analytics and then resetting consent only removed storage/cookies and reset
`gaLoaded`. The already-loaded Google tag remained active; accepting again appended
another script. Browser reproduction confirmed the disable flag was absent.

Withdrawal now sets the measurement-specific `ga-disable-...` flag before clearing
cookies. Reacceptance reenables the existing instance without injecting another tag.
The command queue now uses Google's documented `Arguments` format. Cookie deletion
also covers parent domains: a browser test on `www.review.test` demonstrated that
host-only deletion leaves `.review.test` cookies behind, then verified the fix.
The Google library is stubbed in these regression tests; they verify our integration
controls rather than Google's internal implementation or receipt of network events.

Reference: [Google's Analytics disable control](https://developers.google.com/tag-platform/security/guides/privacy).

### 2. Remote snapshots accepted executable link URLs (medium, defense in depth)

Files: `site/lib/githubSchema.ts`, `site/lib/scholarSchema.ts`, `site/lib/snapshotUrl.ts`.

Snapshot `htmlUrl` fields accepted arbitrary strings. A mocked future GitHub snapshot
put `javascript:alert(1)` into a rendered release link through the normal live updater.
This demonstrates an unsafe navigation sink, not a CSP bypass or successful script
execution. Exploitation requires influence over the fetched snapshot/upstream data.

Navigable snapshot URLs now accept only absolute HTTP(S) URLs at both build-time and
browser parsing boundaries. A rejected snapshot preserves the server-rendered fallback.
GitHub's free-form `homepage` metadata remains a string because it is not rendered as a
link; tightening it initially rejected a real snapshot, caught by the full browser suite
and corrected with a compatibility regression test. If this field becomes navigable,
it must go through URL validation too.

### 3. Keyboard activation hijacked links inside cards (medium usability impact)

File: `site/lib/detailModal.ts`.

On the projects page, focusing an external link and pressing Enter opened the parent
project modal and prevented native link activation. The keyboard listener now handles
only events targeting the card itself. Nested links retain their native behavior.
A Chromium test failed before the fix and passes afterward.

### 4. Mobile consent banner occupied nearly half the viewport (medium usability impact)

File: `site/styles/global.css`.

At 390 x 844 pixels the banner was approximately 393 pixels tall. Its paragraph's
`flex-basis: 320px`, intended as a desktop width, became a minimum allocation along the
vertical axis in the mobile column layout. The mobile paragraph now uses `flex: none`.
The regression checks banner height and visibility of both consent buttons. Final
Chromium measurement was approximately 136 pixels; the corrected screenshot was inspected.

### 5. Duplicate snapshot loaders consolidated (maintainability/reliability)

Files: `site/lib/liveSnapshot.ts`, `githubLive.ts`, `scholarLive.ts`, `citationsLive.ts`.

Three copies of fetch, validation, error fallback, memoization, and freshness comparison
now share one implementation. Each snapshot keeps its own cache and existing exported
API. Browser reads now have the same ten-second timeout policy as build-time reads.
Existing snapshot tests plus an abort regression cover the shared policy.

## Outstanding findings and proposed fixes

### A. Deployment can leave the site offline after a failed build (high availability impact)

`deploy.sh:13` stops nginx before the build at line 22. With `set -e`, a failed dependency
install/build prevents the final restart. The build also writes directly into `dist/`.
Simply moving `compose down` later would still expose partially replaced files if nginx
keeps serving that directory during the build.

Proposed fix: build and validate in a separate release directory, preserve the previous
release, then switch nginx to the completed release and provide rollback. Test an
intentionally failed build while repeatedly requesting the currently served site.
Not changed here: this requires validating the host's Docker mount and rollout setup.

### B. HTTP deep links miss the HTTPS redirect (medium, resolved in follow-up)

`nginx/livermetabolism.com:19` and `nginx/nginx_ssl.conf:59` use `location = /`, which
matches only the root request. `/publications/` and other deep links do not enter that
redirect. The primary hostname is also absent from the host config's HTTP `server_name`
list; its behavior depends on other/default virtual hosts.

Proposed fix: use `location /` for the redirect while keeping the more specific ACME
challenge location, and include `livermetabolism.com` in the HTTP host list. Verify with
`nginx -t` and requests to root/deep paths and ACME paths for each configured hostname.
Implemented in the follow-up: both configurations use `location /`, and the canonical
hostname is included in the HTTP host list. Local nginx containers passed syntax checks
and 120 HTTP checks across all ten hostnames, including query strings and existing/missing
ACME challenges. The same harness reproduced 63 failures before the changes. Production
configuration has not been reloaded.

### C. Python/Zod validation has drifted (medium data correctness impact)

`site/lib/schemas.ts:25`, `:42`, and `:82` do not match `src/data.py`:

| Sample record | Zod result | Python result |
| --- | --- | --- |
| Publication with `year: null` | Accepted as `0` | Rejected |
| News with `date: null` | Accepted as `1970-01-01` | Rejected |
| Person with `orcid: invalid` | Accepted | Rejected |

All three differences were executed against the actual models using isolated records.
Python also validates publication DOI syntax, while the corresponding Zod field is an
optional string. Python strips string whitespace globally; Zod does not. CI's Python
validation protects its deployment path, but a standalone Astro build is weaker than
the README's claim of equivalent validation.

Proposed fix: define shared valid/invalid fixtures consumed by both suites; reject null
required values before coercion and mirror identifier validators. Consider generating
common constraints from a single specification rather than maintaining two independent
schema definitions. Current real data passes both suites.

### D. Privacy documentation omits automatic third-party resource requests (medium, resolved in follow-up)

`site/components/Head.astro` loads Google Fonts on every page. Live snapshot readers
contact `raw.githubusercontent.com`; news previews and embedded players contact Google/
YouTube. `site/pages/privacy.astro` section 4 describes external offers only as links
that users click to leave the site, so it does not describe these actual resource loads.
This is a technical documentation mismatch, not a legal-compliance conclusion.

Implemented in the follow-up: the privacy page describes Google Fonts, GitHub-hosted
snapshots, YouTube previews/players, request triggers and transmitted metadata, and their
independence from Analytics consent. It also explains local consent storage and the
withdrawal behavior. The Analytics IP description was corrected against Google's current
documentation and the statutory abbreviation updated to TDDDG. Resource loading behavior
and hosting have not changed.

### E. nginx configurations duplicate behavior and have already drifted (low/medium)

`nginx/nginx_ssl.conf` retains Jekyll comments and a different cache/header setup from
`nginx/nginx.conf`. The latter relies on the host proxy for `X-Frame-Options` and
`X-Content-Type-Options`; direct container serving lacks those protections. The legacy
TLS config's `/assets/` location sets its own `add_header`, which also requires careful
review of inherited headers for the actual nginx version/configuration.

Proposed fix: document which entry points are supported, remove obsolete configuration
only after confirming it is unused, and share security headers explicitly. Verify headers
on normal pages, assets, redirects, and error responses for every supported serving path.

### F. Python document generators share plumbing through an unrelated generator (low)

`src/cv/list_of_software.py:11` owns `read_data` and `is_missing`, which other generators
import. Presentation and poster generators duplicate HTML-to-Typst author conversion,
selection, numbering, and file writing. The publication converter differs intentionally
in highlighting, so it should not be merged blindly.

Proposed fix: extract loading/missing-value helpers and a parameterized author formatter
into a small shared module. Preserve publication-specific formatting with golden output
fixtures. No broad generator rewrite was made during the website fixes.

## Security controls reviewed

- Static output limits server-side attack surface; no application login/API/database
  service is defined in the reviewed site.
- CSP restricts script sources and uses hashes; snapshot text is generally rendered
  with textContent/Vue interpolation. The URL issue above was a separate boundary.
- Detail routes reject path traversal shapes before fetching fragments.
- Repository-authored HTML intentionally uses `v-html`/`set:html`; data schemas do not
  sanitize this markup. Treat YAML editing rights as code-publishing rights. DOMParser
  adoption in the modal is not itself an HTML sanitizer.
- GitHub API credentials are used by tooling, not passed as site component props.
  This review did not perform an exhaustive git-history secret scan.
- Dependency lockfiles and Dependabot configuration exist. No dependency version was
  changed without an advisory result and compatibility verification.
