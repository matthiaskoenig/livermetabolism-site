# Internationalization (i18n)


The site is English (default, unprefixed) and German (`/de/`). `data/*.yml` and `site/lib/i18n/ui.en.ts` are the English source; nothing German is ever hand-authored against that source directly (the two legal pages invert this, see below) - German is *generated* into `i18n/de/*.yml` and `i18n/de/ui.yml`, and `i18n/TRANSLATION.md` is the authoritative, dense guide to that workflow (established vocabulary, gender-inclusive style rules, what is never translated, HTML-bearing vs. plain-text fields, placeholders) - read it before touching any German text, and before extending anything below.

- **Routing**: `site/lib/i18n/locales.ts` defines `Locale = 'en' | 'de'`, `LOCALES` and `DEFAULT_LOCALE` ('en'). Every page under `pages/[...locale]/` calls `localePaths()` (`site/lib/i18n/routes.ts`) as its `getStaticPaths`; the default locale's rest param is `undefined`, which Astro renders unprefixed ("/publications/"), every other locale under its own prefix ("/de/publications/"). `localeUrl(locale, path)`/`urlFor(locale)` build a path with that prefix (and the deploy's base path, via `url()`); `stripLocale(pathname)` does the reverse, and `switchPath(locale, pathname)` (used by the language switch) composes the two to find "the same page in the other language". Never hand-write a `/de/...` href - always go through one of these, the same way non-i18n code never hand-writes a root-relative href (see "Links and assets" above).
- **Data tables**: `site/lib/i18n/fields.ts`'s `TRANSLATABLE` is the single registry of which `<table>.<field>` pairs carry translatable prose (e.g. `teaching: ['title', 'content', 'caption', 'funding']`) - the five bibliographic tables (publications, posters, presentations, abstracts, panels) and `tags.tag` are deliberately absent (a paper's title is its citation identity; `tag` is simultaneously a reference key, a URL slug and a chart series name). `site/lib/i18n/content.ts`'s `loadCatalog(locale, table)` reads `i18n/<locale>/<table>.yml` (one flat map of row id -> field name -> `{sha, text}`, empty/missing entries falling back to English) and its `overlay()` merges a catalog onto the English rows Astro's content layer produced, field by field, for every `get*(locale)` wrapper in `site/lib/data.ts`. `sha` (`site/lib/i18n/sha.ts`'s `sourceSha()`) is a hash of the *English* source value, not the German text - it is what lets `npm run i18n:check` tell a translation that is merely outdated (`stale`, sha mismatch) from one that was never written (`missing`) without a human re-reading every row.
- **The UI catalog**: `site/lib/i18n/ui.en.ts`'s `en` object is the English source of every chrome string (nav labels, button text, ARIA labels, plural templates, …), flattened to dotted keys (`nav.publications`, `status.publication`, `tags.label.digitalTwins`) by its own `Leaves<T>` type. `i18n/de/ui.yml` mirrors it key-for-key as the same `{sha, text}` shape as the data catalogs. `site/lib/i18n/catalog.ts`'s `loadUi(locale)`/`uiFor(locale)` (`{ t }`, a `TFn`) throws at build time if the German key set does not *exactly* match the English one - a stricter, always-on guard on top of `npm run i18n:check`. `site/lib/i18n/slices.ts`'s `slices(t)` bundles narrow per-component string groups (`teachingCard`, `fundingCard`, `publicationRow`, …) from that `t`, so a component takes a small serializable prop object rather than the whole ~500-key catalog (keeping it out of `astro-island` props, and keeping the machine value used for CSS classes/lookups - `pub.status`, `teaching.type`, `funding.role` - separate from its translated display label). A plural pair is two flat keys, `xOne`/`xOther` (e.g. `pub.citedOne`/`pub.citedOther`), chosen by the caller with `count === 1 ? ... : ...`, not a nested pluralization object - `fmt()` (`site/lib/i18n/format.ts`) only does `{placeholder}` interpolation. A template read from the DOM for a browser-side live refresh (the citation/release/star counts, see "Live GitHub and Scholar data") carries both plural forms as separate `data-*-template-one`/`-other` attributes for the same reason.
- **Drift guard**: `npm run i18n:check` (`scripts/i18n-check.ts` over `scripts/lib/i18n-check.ts`) is the standalone Node script (import-extension `.ts`, so it cannot share `site/lib/i18n/content.ts`/`catalog.ts` directly - `scripts/lib/i18n-check.ts` has its own parallel YAML readers that must be kept in sync with them by hand, see the `NOTE` comments on each) that audits every data table plus the UI catalog for `missing`/`stale`/`orphaned`/`unknown-field` entries and exits non-zero if any exist; it is what `i18n/TRANSLATION.md` tells a translator to run until clean. `i18n/de/pages/*.yml` (the legal pages, below) are **not** covered by this guard or by `loadUi()`'s key-set check - keep that gap in mind before trusting "`i18n:check` passes" to mean the whole site's German is current.
- **Regenerating German**: the `.claude/skills/translate-de` skill (`.claude/skills/translate-de/SKILL.md`) is the only sanctioned way to write `i18n/de/*.yml`/`i18n/de/ui.yml` by hand-editing them directly is a workflow violation the next regeneration will silently overwrite. It runs `npm run i18n:check`, translates exactly the entries it lists (per `i18n/TRANSLATION.md`), and writes each entry's `sha` from the current English source (`node scripts/i18n-sha.ts <table> <id> <field>` prints the sha/value pair for one field without guessing). A hand-edit for pure cross-catalog terminology consistency (the same English text rendered two different ways in two tables) is the one exception the review process allows explicitly per instance - it does not change the English source, so the existing `sha` stays valid and no regeneration is needed, but it must still be followed by `npm run i18n:check` to confirm nothing went stale, and the resolved term added to `i18n/TRANSLATION.md`'s glossary so it cannot re-drift.
- **The legal pages invert the direction**: `i18n/de/pages/impressum.yml`/`privacy.yml` are the *source*, authored directly in German because it is the legally binding text for a site operated under German law; `i18n/en/pages/` is *generated from the German*, the only place on the site where English is the target. `site/lib/i18n/pages.ts`'s `loadPage(locale, page)` knows this via `PAGE_SOURCE_LOCALE`, and a missing/lagging English key falls back to that page's own source locale (German), never to nothing - a legal notice must never render blank. `site/pages/[...locale]/impressum.astro`/`privacy.astro` render `page.heading` etc. as both the `<h2>` and the `<title>` (via `Base`'s `title` prop), and show `page.bindingNotice` ("only the German version is legally binding") on every non-German locale.
- **Language switch, twice**: `LanguageSwitch.astro` (EN/DE, real `<a>` links via `switchPath()`, so it works with no JavaScript and middle-clicks like a link) is rendered by `TopNav.astro` on every page. A native `<dialog>` shown with `showModal()` (the detail modal, see "The detail modal" above) makes everything outside it, including the fixed navbar, non-interactive - so `DetailModal.astro` carries its own second copy in the modal header, styled for the header's light background, for a reader who opened the modal and wants to switch language without closing it first. Both read the *current* `Astro.url.pathname` by default; `404.astro` is the one page where that default is wrong (its own build-time route has no real per-locale counterpart, see `robots.txt and LLM files` above), so it passes an explicit `langSwitchPath="/"` override down through `Base`/`TopNav`/`LanguageSwitch`'s optional `path` prop instead, and `noAlternates` to `Base`/`Head` for the same reason (`alternates()` otherwise emits an `hreflang="de-DE"` link to a German 404 that was never built).
- **Tag labels**: a tag's *reference value* (`tags.tag`, e.g. `"Digital Twins"`) is never translated - it is a slug source, a filter value and a chart series key all at once - but its *display label* is German via `tags.label.*` UI-catalog keys, resolved per slug by `tagLabel()` (`site/lib/i18n/tagLabel.ts`, falling back to the tag's own value - never the bare slug - if a slug has no label key yet) and baked into `TagInfo.label` by `getTags()`. Every rendered tag chip, filter button and chart legend/tooltip uses `.label`; only `data-tag`/`?tag=`/`?topic=` matching still reads `.tag`.
